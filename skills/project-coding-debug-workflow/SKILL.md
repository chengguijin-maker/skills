# 项目编码调试工作流

## 1. 工作原则

把开发调试任务当成项目流程的一环，而不是孤立命令。先确认任务来源、项目范围、机型版本、目标分支和期望产物，再决定查资料、抓日志、定位代码、整理自测或准备转测。

默认边界：

1. 9655 内销项目是主线。
2. JuOS 只作系统侧补充。
3. 商显、激光、外销、GTV、其他平台可作方法参考，不能直接写成主线事实。
4. Confluence 是流程和事实主源，Jira 只作状态、责任和问题跟踪佐证。
5. Jira Closed 不是测试、发布或质量闭环。
6. OTA 台账不能直接反推代码分支或构建包。
7. 未经用户明确要求，不执行 `repo sync`、编译、Jenkins、下载版本包、设备升级、adb 写入、串口写入、remount、替换系统文件。

## 2. 入口判断

先按用户描述选择主线。

| 用户意图 | 处理主线 |
| --- | --- |
| 设备连接、remount、串口、升级、替换文件 | 设备调试线 |
| 抓 log、DTV、Audio、HDMI、DP、Dolby、HUI、pstore | 日志体系线 |
| CPU 高、内存涨、UI 卡顿、underflow、开机慢、网页慢 | 性能定位线 |
| undefined symbol、dlopen、so、GDB、core、native 泄漏 | 代码问题线 |
| 分支、构建、IR、OTA、version.txt、MTK tag、回灌 | 构建分支线 |
| 手册、检查表、流程图谱、SOP 汇总 | 正式手册线 |

需要详细路由时读取 `references/sop-routing.md`。

## 3. 标准处理流程

1. 建立任务卡。
   记录任务来源、项目范围、机型、版本、目标分支、复现材料、日志证据、期望产物。

2. 确认资料边界。
   标明哪些来自 Confluence，哪些来自 Jira，哪些是 JuOS 或其他平台参考，哪些还没有证据。

3. 选择专项 SOP。
   按入口判断选择设备、日志、性能、代码、构建分支之一；复杂问题可以组合多条线。

4. 先取证再结论。
   不用单条日志、一次 top、一次 trace、一次火焰图、一个 Jira 状态直接写根因或闭环。

5. 输出时区分事实、推断和待确认。
   每个关键结论要能回到页面、文件、命令输出或用户确认。

6. 给出下一步最小验证动作。
   优先选择只读、低风险、短超时动作。需要设备写入或长任务时先说明风险并等待明确要求。

## 4. 开发任务卡字段

最小字段：

| 字段 | 说明 |
| --- | --- |
| 任务来源 | Jira、DTV、CR、PLM、测试、市场、临时调试 |
| 项目范围 | 9655 内销主线或参考项目 |
| 机型版本 | 样机、软件版本、user 或 userdebug、构建时间 |
| 目标分支 | master、IR、OTA、新品鉴定或待确认 |
| MTK 对齐 | MTK tag、MTK 分支、`version.txt` |
| 现象证据 | 步骤、概率、日志、截图、视频、trace |
| 代码范围 | 仓库、模块、进程、包名、so、配置项 |
| 修改类型 | 临时验证、配置变更、代码修复、性能参数、MTK patch |
| 自测交接 | 用例、结果、未覆盖范围、风险、回归建议 |
| 闭环证据 | Review、commit、构建包、测试报告、发布观察、回灌 |

## 5. 常见输出

按任务规模选择输出。

1. 简短任务：给任务卡、判断、下一步动作。
2. 调试任务：给取证方案、命令边界、风险和回滚要求。
3. 代码任务：给定位路径、符号或库分析、修改建议、自测和 Review 检查。
4. 分支构建任务：给目标分支、version.txt、MTK tag、构建产物和合入确认字段。
5. 流程沉淀任务：输出 SOP、证据矩阵 CSV、风险和待补证据。
